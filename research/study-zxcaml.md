"# ZxCaml subset + native-execution characterization

## 1. SUBSET (docs/02-grammar.md + docs/00-overview.md, cross-checked against examples/ and stdlib/core.ml)

**Accepted today** (post-P9 baseline, wire sexp 1.5/1.6/1.7):
- `let` / `let rec ... and ...` (top-level and nested, mutually recursive groups), `external name : ty = "zig_symbol"`.
- Functions: `fun x -> e`, curried multi-arg functions represented as nested lambdas; **first-class closures** (examples/first_class_closure_pass.ml, first_class_closure_return.ml, closure_adt.ml, captured_loop.ml all exercise closures/capture).
- ADTs: `type color = Red | Green | Blue`, parametric `'a tree = Leaf of 'a | Node of ...` (recursive ADTs supported; "full general recursive type inference remains intentionally narrow").
- `match` with nested/guarded (`when`)/or (`|`)/alias (`as`)/literal patterns, arbitrary scrutinees.
- Tuples (construction, destructuring, `fst`/`snd`), records (construction, field access `r.x`, functional update `{r with x=v}`, destructuring) — but **no general mutable-field writes** `r.x <- v` (only the special-cased Solana `AccountFieldSet` path).
- Controlled mutable `int` arrays only (`[| |]` literal, `Array.get/set`, `.()`/`.() <-`, `Array.length`, `Array.make N init` with N a non-negative int **literal**); `Array.init`/polymorphic arrays/dynamic-size `Array.make`/`Array.unsafe_get` rejected today. docs/22-generic-arrays-plan.md is a *plan* (not yet landed) to widen element types to bool/string/bytes (slice 1) then records/tuples (slice 2); still no `'a array`, no `Array.map`/slicing, no dynamic sizing ever.
- `ref` cells (ADR-015 R10): `ref e`, `!r`, `r := v`, but **only** `int` or `bool` element type, single-cell, no cross-function aliasing; string/record/list/polymorphic refs rejected (E0013). (Note: examples/m0_unsupported.ml = `let x = ref 0` is flagged as the CI "expected to fail" fixture — likely stale relative to R10, or illustrates a residual ref restriction not fully resolved in the example corpus.)
- Primitive ops: `+ - * / mod`, bitwise ops, comparisons, string concat `^`, `while`/counted `for` loops (lowered without OCaml runtime), `assert`.
- Polymorphism: parametric type declarations (`'a tree`, `'a box`) are accepted; **but** polymorphic *functions* fall back to weak/heuristic typing when unresolved (see examples/lambda_type_demo.ml comment: an unconstrained `identity x = x` gets wire type `(any)` and "legacy heuristic-based behavior" — polymorphism is tolerated, not fully generic/parametric at the IR level).
- String/bytes: `String.length/get/sub`, `Char.code/chr`, `Bytes` ops (`Bytes.length`, `Bytes.blit`, `Bytes.of_string`, etc. — exercised in examples/bytes_*.ml). No user-visible `float` type anywhere (`rg` for `Int32|Int64|float|Float` in docs/02-grammar.md and stdlib/core.ml returns nothing) — **int is a single width, represented as signed 64-bit under the frontend; no float, no Int32/Int64 sub-widths.**
- `open Foo` of a **sibling user file only** (ADR-016, docs/21) — resolves to `<entry_dir>/foo.ml`; this is the one exception to "no modules."

**Rejected** (docs/02-grammar.md section 5, and docs/00-overview.md section 6 "out of scope forever"):
- `exception`, `try`, `raise` — explicit reject with diagnostic `Texp_try is not supported ... exceptions are out of scope`. Confirmed no exception/try/raise keyword actually appears in any example .ml file (checked div_zero.ml, arith_wrap.ml, assert_demo.ml — zero hits; earlier substring grep hits were comment prose, not code).
- `module sig struct functor include` (except the one ADR-016 sibling-file `open`), first-class modules, GADTs, polymorphic variants, private types, type constraints, module signatures.
- `class object method inherit initializer`, `lazy`, labelled/optional arguments outside a whitelisted stdlib surface, local opens, dotted opens (`open A.B`).
- **GC-dependent features**: no garbage collection at all (arena-only memory model, hidden from user); this rules out anything assuming boxed/GC'd representations beyond what the arena lowering supports.
- **`printf`/`Printf`**: zero references anywhere in docs/02-grammar.md, stdlib/core.ml, or README.md — not part of the subset (no format-string machinery; account/data logging goes through separate Solana log intrinsics, not stdout).
- Partial/labeled/optional application: "partial/labeled/optional application is still out of scope" — explicit line in the grammar doc's function-application row.
- Mutable record-field writes outside the `AccountFieldSet` witness path; instance-variable writes; override expressions.

## 2. STDLIB (stdlib/core.ml)

Provides, as ordinary OCaml-subset code type-checked by upstream `ocamlc`:
- `Option` (map, bind, fold ~none ~some, is_none, is_some, value, get [loops via `unreachable`, not an exception, to signal the impossible-None-path]).
- `Result` (map, map_error/map_err, bind, is_ok, is_error, ok, error).
- `List` (length, map, filter, fold_left, rev via fold_left, append, hd/tl [again via `unreachable` recursion instead of exceptions], nth, exists, for_all, find, sort [manual insertion sort], combine, split) — all hand-written recursive OCaml, no reliance on Stdlib.List.
- `String` (length/get via `%string_length`/`%string_safe_get` externals, sub delegates to `Stdlib.String.sub`), `Char` (code/chr via `%identity` externals).
- `Fun` (id, const, flip).
- Custom `^` operator rebound to `Stdlib.(^)`.
- `Map`/`Set`: full hand-rolled AVL-ish balanced-tree implementations (not reusing `Stdlib.Map`/`Stdlib.Set` functors — consistent with "no functors" rule; these are monomorphic-record-carrying-comparator trees, not functorized).
- Solana-domain modules: `Account`, `AccountMeta`, `Pubkey` (zero, token_program constant, of_hex), `Error`, `Pda`, `Cpi` (with `external` FFI bindings to Zig runtime symbols like `Cpi.set_return_data`), plus record types for `account`, `instruction`, `clock`, `rent`, `epoch_schedule`, etc.
- **Naming/convention pattern**: instead of raising exceptions for impossible cases (`List.hd []`, `Option.get None`), the stdlib uses `let rec unreachable () = unreachable ()` (an infinite non-productive recursion) as the "exception-free bottom" — this is the idiomatic ZxCaml way to represent partial functions without `exception`/`raise`. Domain-object accessors follow a `Module.field_or_predicate account_value` convention (e.g., `Account.is_signer`, `Account.has_key`). The comment header states core.ml is "intentionally valid upstream OCaml so ocamlc can type-check it as an oracle."

## 3. NATIVE PATH

- **Build/run natively**: per README.md "Native execution comes for free" — because every accepted ZxCaml program is by construction valid OCaml (parsed/type-checked by upstream `compiler-libs`, ADR-001) and a working OCaml toolchain is already required for `omlz` itself (ADR-010), the **identical `.ml` file** can be compiled/run with plain `ocaml`/`dune` (`dune exec`) or OxCaml, producing a native x86_64/arm64 binary for local testing/fuzzing/REPL — with NO dedicated ZxCaml x86 backend. Determinism between the native path and the BPF path is asserted (not just hoped) via "the determinism invariant (ADR-008)": both paths are guaranteed to compute the same result for any accepted-subset program.
- **BPF path (the real deliverable)**: `scripts/omlz.sh` (per ZXCAML.md) sets up zig 0.16.0 + `~/.local/bin` on PATH, selects opam switch `zxcaml-p1`, cd's to the repo root, and execs `zig-out/bin/omlz`. Canonical command: `zig-out/bin/omlz build examples/solana_hello.ml --target=bpf -o sh.so`, producing an ELF eBPF/SBPF `.so` (verified with `file sh.so`).
- **`omlz check`** is the fast parse/type-check-only gate (no codegen): confirmed "`omlz check` exit 0 does NOT prove codegen; only `omlz build --target=bpf` does" (ZXCAML.md trap #4). `check` has flags: `--no-alloc` (prove zero arena allocation, INSTALLING.md verification: `zig-out/bin/omlz check --no-alloc examples/arith_wrap.ml`), `--report=cu,stack|all` (static compute-unit/stack budget report, opt-in, exit code unaffected — docs/06-bpf-target.md), `--emit=core-ir` (dump Core IR, docs/03-core-ir.md), `--error-format=json` (used by LSP, docs/17-lsp-latency.md).
- **opam switch `zxcaml-p1`** (per INSTALLING.md): created by `init.sh` as `opam switch create zxcaml-p1 5.2.1 -y`, with `ocamlfind` installed on top; used purely to build the `zxc-frontend` OCaml glue binary against upstream `compiler-libs`. It is explicitly *not* a general opam consumer switch (docs/00-overview.md section 2: "Not an opam consumer... existing opam packages will not just work"). The **default switch** is implicitly whatever `ocaml`/`dune` the developer already has for running the SAME .ml file natively (README's native-execution path) — the repo does not document a separate "default switch" setup; it's just the user's ambient OCaml/dune/OxCaml install, orthogonal to `zxcaml-p1`. Nothing in the repo suggests `zxcaml-p1` carries any extra opam packages beyond `ocamlfind`/compiler-libs (docs/08-roadmap.md zh mirror explicitly states "zero third-party opam dependencies" for the frontend bridge).

## 4. MULTIFILE (docs/21-multifile-modules-plan.md, ADR-016)

- **State: landed as "option B" — frontend-level `open Foo` only, NOT true modules.** A ZxCaml "project" CAN today span several `.ml` files, but only via a restricted mechanism:
  - A top-level `open M` in the entry file (or a dependency) where `M` is an **uncapitalized-name-derived sibling file** (`open Vault_types` -> `<entry_dir>/vault_types.ml`) is resolved, discovered recursively (DFS), and its Typedtree is compiled to `.cmo`/`.cmt` and **joined into one flat sexp/module** ahead of the entry file's own declarations.
  - Reserved: `open` of any bundled stdlib module name (`Core`, `Generators`, `Account`, `Pubkey`, `Crypto`, etc.) is rejected E0103, as is a user file that shadows those names.
  - **Flat namespace, no name mangling**: duplicate top-level value/type/constructor names anywhere in the closure are a hard error (E0102) rather than being disambiguated — there is no real per-module scoping, just source concatenation with collision detection.
  - Dependency edges are `open`-only; using `Foo.x` without `open Foo` does NOT create a dependency edge (`ocamlc` just reports unbound module). `include`, nested/local opens, dotted opens (`open A.B`), and per-file `let%test` blocks stay explicitly out of scope.
  - No `.mli`, no module signatures, no functors, no `.cmi` caching / incremental compilation ("ADR-011 intact") — every build recompiles the whole closure from source.
  - New diagnostics E0100 (unresolved open) / E0101 (open cycle) / E0102 (duplicate name) / E0103 (reserved-name open).
  - Net: **yes, several `.ml` files today**, but it is closer to "textual/typed inclusion with collision checking" than to OCaml's real module system — there is exactly one namespace after resolution, and it is explicitly *not* the reopened "module/functor" out-of-scope area from docs/00-overview.md.

## 5. HARNESS FIT (differential-testing harness: typed-AST QCheck generator + pure reference interpreter + process spawning/diffing)

| Component | Feasibility inside ZxCaml subset | Blocking / missing feature |
|---|---|---|
| (a) Typed-AST **generator with randomness (QCheck)** | **Full-OCaml-only.** | QCheck itself is an opam package/functor-heavy PBT library (uses first-class modules / GADT-ish generator combinators internally in places, and definitely uses exceptions for shrinking control flow and `Random.State` refs of non-int/bool element types) — none of that is reproducible in the ZxCaml subset (no opam consumption per docs/00-overview.md section 2, no functors, no GADTs). This piece MUST run under plain OCaml, not `omlz`. |
| (b) **Pure reference interpreter over an expression AST** | **Largely ZxCaml-subset-feasible for the CORE eval loop** — recursive `match`-based evaluation over an ADT (`type expr = Lit of int | Add of expr*expr | ...`) is exactly the shape ZxCaml is built for (recursive ADTs + match + let rec are core-subset). BUT: if the interpreter needs an **environment as an association list keyed by string with lookup that can fail**, the idiomatic-OCaml version raises `Not_found`/a custom exception on unbound variable — that must be rewritten to return `option`/`result` (ZxCaml has no `exception`/`raise`/`try`) or to use the stdlib's `unreachable ()` trick for the impossible case. If the interpreter represents environments as a real mutable `Hashtbl`, that is **out of subset** (no Hashtbl in stdlib/core.ml, no polymorphic hash-based structures) — must fall back to the hand-rolled `Map`/`Set` AVL trees already in `stdlib/core.ml`, which ARE subset-legal and directly reusable. |
| (c) **Process spawning (rustc/node) + file IO + diffing** | **Full-OCaml-only.** | Process spawning (`Unix.create_process`/`Sys.command`), file IO (`open_out`, `In_channel`), and shelling out to `rustc`/`node` all depend on the OCaml/Unix runtime and are explicitly outside ZxCaml's GC-free, syscall-restricted BPF execution model (docs/00-overview.md: "no OCaml C runtime"; docs/08-roadmap.md zh: "no syscalls" in the BPF-shaped constraints). This is native-OCaml-only harness glue. |

**Maximal-subset recommendation**: the largest coherent piece that can be written to compile under BOTH `omlz` (BPF/native-execution-comes-for-free path) AND stock OCaml/dune is the **expression-AST type declarations + the pure evaluator/interpreter core + any pretty-printer built from string concatenation (`^`) and the stdlib's `int_to_string`/`hex_of_int`-style manual formatting** (stdlib/core.ml already contains exactly this pattern for base-10/hex int-to-string — no `Printf`, no `string_of_int` reliance, hand-rolled recursive digit peeling). Concretely: put `type expr = ...` (ADT), `let rec eval env e = ...` (match + `let rec`, environment via the subset's `Map` module or association-list `List` ops), and `let rec pp_expr e = ... ^ ...` (string-concat pretty printer) all in ONE `.ml` module using only: ADTs, tuples/records, `match`, `let rec`, the subset `List`/`Map`/`Option`/`Result`/`String`/`Char` stdlib surface, and string `^`. Avoid: `exception`/`raise` (return `option`/`result` instead), `Hashtbl`, floats, `Printf`, functors, and any generic polymorphic container beyond what `Map`/`Set` already provide monomorphically-per-comparator. That module then satisfies the README's "native execution comes for free" guarantee (`dune exec` runs it identically to `omlz check`/`omlz build`), giving a shared, dual-compiled, ADR-008-determinism-guaranteed core between the ZxCaml toolchain and the differential harness's OCaml-only driver (a/c) code.

## zxlint trap classes

`zxlint` is not referenced in `docs/*.md` at all (confirmed via `rg zxlint docs/*.md README.md` — zero hits); it is documented only in the repo-root `ZXCAML.md` operating card, which lists the **four codegen traps** it pre-screens (1-3) plus the check-vs-build distinction (4):
1. A unit conditional wrapping a data write fails BPF codegen (`UnsupportedExpr` at build time) — writers must be straight-line; move the guard to the caller.
2. Top-level `let` constants are invisible inside helper functions in emitted Zig — only the entrypoint sees them; must be rebound locally in each helper.
3. Account-data writes must go through witness intrinsics (`read_u8`, `read_u64_le`, `write_u64_le`, `set_account_data`) matched BY NAME by `omlz`, which discards their bodies; real `Bytes` ops are for scratch buffers only, not account-data witnessing.
4. `omlz check` exit 0 does not prove codegen — only `omlz build --target=bpf` does.
`zxlint --errors-only FILE.ml ...` pre-screens traps 1-3 (warnings never block; a `zxlint-gate.py` PreToolUse hook enforces it on `omlz ... build --target=bpf ...` Bash invocations, bypassable per-command with a literal `[skip-zxlint]` suffix for deliberate trap probes)."
