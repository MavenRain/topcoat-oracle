## 1. Pipeline

**Input.** `expr!{ <syn::Expr> }` (`crates/topcoat-runtime/macro/src/lib.rs:7-14`) parses one Rust expression via `syn::parse_macro_input!(tokens as topcoat_runtime_grammar::expr::Expr)`, where `Expr` is `struct Expr { inner: syn::Expr }` (`grammar/src/expr.rs:35-45`) — i.e. it accepts the full `syn::Expr` syntax, then whitelists shapes only during lowering (unsupported shapes hit a catch-all `other => Err(...)` at `grammar/src/expr.rs:154`). It is normally reached indirectly through `view!`'s `$(...)` syntax (`macro/docs/expr.md:1-2`), but `expr!{...}` itself is a standalone `#[proc_macro]` and can be invoked directly.

**Output.** `Expr::expr_to_tokens()` (`grammar/src/expr.rs:54-124`) emits ONE Rust `TokenStream` containing *both* halves:
- Real Rust tokens (`rust`) — ordinary Rust that runs server-side over `Surrogate`-wrapper types, wrapped at the top with `topcoat_runtime::Surrogate::into_real(#rust)` unless the whole expression is a closure (`grammar/src/expr.rs:60-62`).
- A JavaScript source **string** (`js: String`) built up character-by-character in the same recursive `dispatch` pass (`grammar/src/expr.rs:128-158`), spliced into the Rust tokens as a string literal argument to runtime helpers `__js(__parts, #js)` / `__js_unescaped` (`grammar/src/expr.rs:71-118`; helpers at `crates/topcoat-runtime/src/lib.rs:36-61`). At render time these write the JS text into an HTML comment delimited by `::topcoat::expr::start("<js>")` / `::topcoat::expr::end` markers, parsed back out client-side by regex (`browser/src/comment.ts:19-21,50-57`).

**The "IL" is literally JavaScript source text**, not a bytecode/instruction format — there is no separate IL grammar. `grammar/src/expr/*.rs` is a syntax-directed translation: each `dispatch` arm appends real JS syntax fragments (e.g. `".add("`, `".dehydrate())"`, `"while ("`) directly into the `js: &mut String` accumulator while simultaneously building the mirrored `rust: TokenStream`. The eventual JS text is evaluated client-side with `new Function("cx", "return " + js + ";")` (four call sites: `browser/src/binding.ts:27`, `browser/src/event.ts:14`, `browser/src/scope.ts:93`, `browser/src/text.ts:15`) — a single free variable `cx` (a `Context` instance, `browser/src/context.ts:16-46`) is the sole runtime surface reachable from generated code (comment at `context.ts:10-15` states this is deliberate: "keeps non-context globals inaccessible from inside `new Function`").

**Type-checking is 100% deferred to rustc — there is no independent checker.** The grammar/macro layer performs zero type inference; `expr_method_call.rs:40` blindly emits `quote!{ (#receiver).#method(#(#args),*) }` for *any* syntactic method call, and `expr_binary.rs`/`expr_unary.rs` emit real Rust operators/method calls (`add`/`sub`/`eq`/`not`/`neg`/`deref`) over `Surrogate`-wrapper newtypes (`crates/topcoat-runtime/src/surrogate/_f64.rs`, `_bool.rs`, `_str.rs`). If the receiver's Rust surrogate type doesn't implement the called method, the *emitted Rust code* fails to compile with rustc's normal error — that is the macro's only type check. Critically, **the JS half has no static check at all**: `js.push_str(method)` (`expr_binary.rs:37`) / `write!(js, ".{method}(")` (`expr_method_call.rs:27`) copies the method name into the JS text unconditionally; whether a matching method exists on the TS mirror class is discovered only at browser runtime (`TypeError: x.foo is not a function`) or is checked nowhere at all if silently wrong-but-present. Parity between the two sides is maintained purely by hand (TS classes in `browser/src/surrogate/*.ts` mirroring Rust surrogate impls in `crates/topcoat-runtime/src/surrogate/*.rs`) plus string-content assertions in `macro/tests/expr.rs` (e.g. `assert!(html.contains(".toggle()"))`, line 22).

## 2. Supported subset (grammar/src/expr.rs:134-155 dispatch table is exhaustive; anything else -> compile error)

- **Literals** (`expr_lit.rs:15-31`): `Lit::Float` (→ `f64`), `Lit::Bool`, `Lit::Str`. **No integer literals at all** — `other => Err(...,"unsupported literal type")` (`expr_lit.rs:30`); doc confirms "integer literals are not accepted, so write `1.0` rather than `1`" (`macro/docs/expr.md:43,65`). Numeric type is exclusively `f64` — no `i32/i64/u32/u64/usize` anywhere in the vocabulary.
- **Operators** (`expr_binary.rs:19-31`, `expr_unary.rs:14-19`): binary `+ - * /` (→ `.add/.sub/.mul/.div`, real Rust arithmetic operators mirrored), `== != < <= > >=` (→ `.eq/.ne/.lt/.le/.gt/.ge`, called as `(#left).#method(&#right)`); unary `!` (`.not`), unary `-` (`.neg`), unary `*` deref (`.deref`). No bitwise ops (`&`,`|`,`^`,`<<`,`>>`), no `&&`/`||` logical short-circuit operators, no compound-assign (`+=` etc.), no `=` assignment expression at all — mutation only happens through `Signal` methods.
- **Calls**: plain function/closure `.call(...)` syntax (`expr_call.rs:46-53`), plus special-cased single-segment paths `Some(...)`/`Ok(...)`/`Err(...)` that construct `Option`/`Result` surrogates directly (`expr_call.rs:17-44`, JS `cx.some`/`cx.ok`/`cx.err` from `context.ts:31-45`). Turbofish is rejected (`expr_method_call.rs:16-21`); multi-segment paths / generic args (except `None::<T>`) are rejected (`expr_path.rs:26-55`).
- **Method calls**: syntactically unrestricted (any `.name(args)`); semantically limited by what surrogate types implement. Documented vocabulary (`macro/docs/expr.md:41-51`): `f64` arithmetic/cmp/neg; `bool`: `!`, `==`/`!=`, `then`, `then_some`; `String`/`&str`: `len`, `is_empty`, `trim`, `trim_start`, `trim_end`, `starts_with`, `ends_with`, `contains`, `to_owned`, comparisons; `Option<T>`: `is_some`, `is_none`, `unwrap`, `expect`; `Result<T,E>`: `is_ok`, `is_err`, `ok`, `err`, `unwrap`, `expect`, `unwrap_err`, `expect_err`; tuples of vocabulary types (`macro/docs/expr.md:48`, impl at `src/surrogate/tuple.rs:13`); `Signal`: `get`, `set`, plus shorthand `toggle` (bool signal), `increment`/`decrement` (f64 signal), `push_str` (String signal) — Rust impls at `src/surrogate/signal.rs:54-107`, TS mirror at `browser/src/surrogate/signal.ts:31-45`.
- **Field access / indexing**: `expr_field.rs` (named `.field` and tuple `.0` → JS `[0]`), `expr_index.rs` (`a[b]` on both sides, no bounds semantics enforced by the grammar).
- **Blocks / bindings**: `Stmt::Local` (`let <ident> = <init>;` only — no destructuring patterns, no `let-else` (`stmt.rs:23-27`), no uninitialized `let` (`stmt.rs:20-22`)); trailing expr (no `;`) becomes the JS `return` (`stmt.rs:41-59`); `Stmt::Item` rejected (`stmt.rs:61-63`). A Rust block expression is wrapped in a JS IIFE `(() => { ... })()` (`expr_block.rs:17-24`).
- **Control flow**: `if`/`else` as an expression, IIFE-wrapped, supports `else if` chains recursively (`expr_if.rs`); `loop` → JS `while (true) {}` (`expr_loop.rs`); `while <cond> {}` (`expr_while.rs`); `break`/`continue` unlabeled only, labels rejected (`expr_break.rs:14-16`; `expr_continue.rs` — same shape); `return <expr>?` (`expr_return.rs`). **`match` is explicitly unsupported** (doc: `macro/docs/expr.md:65`); confirmed by dispatch table having no `syn::Expr::Match` arm (falls into the generic reject at `expr.rs:154`).
- **Closures**: `expr_closure.rs`, optionally `async`, any capture mode, only plain-identifier (optionally typed) parameter patterns (`pat.rs:23-26`); body may be a block or a bare expression.
- **`.await`**: `expr_await.rs` → JS `(await <expr>)`. Presence of `.await` anywhere inside an `if`/block flips that block to an async IIFE `(await (async () => ...)())` via `contains_await.rs`'s `ContainsAwait` visitor (`expr_if.rs:18-26`, `expr_block.rs:16-24`).
- **Escape hatch**: `raw!("<js>", <rust-equivalent>?)` macro (`grammar/src/expr/builtin_macro.rs:38-97`) splices hand-written JS (with `${ident}` interpolation of in-scope bindings) alongside an optional Rust equivalent for server-side eval; without the Rust arg the expression can't run server-side (`macro/docs/expr.md:69-86`).
- **Captured variables**: any identifier not bound inside the expression is resolved as an "external" (`name_resolver.rs:72-105`), serialized via `serde_json` into the JS as a `const` snapshot at render time (`grammar/src/expr.rs:81-120`) — a one-time snapshot, not reactive.
- **Signals**: read via `.get()`/write via `.set()`/shorthand mutators as above; `Signal` values round-trip via a tagged JSON encoding `{t:"Signal", id, v?}` (`browser/src/surrogate/index.ts:22-33,65-69`) hydrated into a `WriteSignal` wrapping `@maverick-js/signals`.

## 3. Semantics risk map (native Rust vs. browser/TS execution)

| Construct | Rust semantics | TS/browser semantics | Divergence risk |
|---|---|---|---|
| `f64` arithmetic (`+ - * /`) | IEEE-754 binary64 (`src/surrogate/_f64.rs:22` macro, plain `self.0 op rhs.0`) | IEEE-754 `number` (`browser/src/surrogate/f64.ts:83-97`, plain `this.v op other.v`) | **None for the arithmetic itself** — both are IEEE-754 doubles, div-by-zero yields `inf`/`-inf`/`NaN` identically on both sides. No `i32/i64/u64` exist in the vocabulary at all, so there is no wrapping/overflow semantics to diverge (confirmed absent, §2). |
| `f64` → text (`Display`) | Rust `Display` for `f64` (shortest round-trip digits, always positional, `inf`/`-inf`/`-0`) | Custom `display()` reimplementation (`browser/src/surrogate/f64.ts:53-78`) that explicitly reverses 5 documented JS/Rust divergences (comment `f64.ts:40-52`, tracked as issue **#237**): exponential-notation threshold, `Infinity`→`inf` spelling, sign of `-0`, and round-half-to-even vs round-half-away-from-zero tie-breaking (uses exact BigInt mantissa decomposition, `f64.ts:6-38`, to detect and correct ties). This is a deliberately-patched risk, not an open one, but any future JS engine change to `toExponential()`/`toString()` edge cases could reopen it. |
| String comparison (`< <= > >=`) | Rust `str` ordering = code-point / UTF-8 byte order | JS default `<`/`>` = UTF-16 code-unit order — **wrong above U+FFFF** (surrogate pairs sort incorrectly). Patched via a custom `compare()` that iterates code points (`browser/src/surrogate/string.ts:16-35`, tracked as **#236**). | Mitigated, but only inside `Str`/`String` surrogate methods; any `raw!` escape hatch that does native `<`/`>` on strings bypasses this fix. |
| `str::len` | Rust: UTF-8 **byte** length (`src/surrogate/_str.rs:64-66`) | TS: `TextEncoder().encode(v).length` — UTF-8 byte length (`browser/src/surrogate/string.ts:5,72-74`) — matches Rust, **not** JS's native UTF-16 `.length` | Correctly mitigated; would have diverged if the naive `.length` had been used. |
| `trim`/`trim_start`/`trim_end` | Rust strips Unicode `White_Space` property set | Patched regex set explicitly reproducing Rust's whitespace set, differing from ECMAScript's (keeps U+FEFF, strips U+0085) — comment cites **#238** (`browser/src/surrogate/string.ts:7-14`) | Mitigated by construction; same caveat as string comparison re: `raw!` bypass. |
| `bool` ops | plain Rust bool logic | plain JS bool logic (`browser/src/surrogate/bool.ts`) | None — no divergence, and no `&&`/`\|\|` short-circuit operators exist in the grammar at all (§2), so short-circuit-evaluation-order questions don't arise for the compiled subset. `then`/`then_some` both eagerly evaluate the Rust closure/value before branching identically to `Bool.then`/`then_some` (`bool.ts:23-30`). |
| `Option`/`Result` `.unwrap()`/`.expect()` | Rust panics (aborts thread) | JS throws a custom `Panic extends Error` (`browser/src/surrogate/panic.ts`), uncaught by any handler shown in the runtime — propagates up through the `new Function` call and (per `effect()` wiring in `text.ts:19-27`, `scope.ts:106-121`) would surface as an unhandled exception inside a Maverick `effect`, not a Rust-style abort/unwind. Message text differs in format from Rust's default panic message (custom `formatPanicValue` for `Result`, `browser/src/surrogate/result.ts:88-103`) — **not** guaranteed to be byte-identical to Rust's `Debug` panic message despite deliberately trying (`{msg}: {formatted debug value}`). | Behavioral risk: panic *recovery*/propagation path (whether it crashes the whole reactive tree vs. one effect) is browser-runtime-specific and has no server-side analogue to compare against, since Rust-side panics simply abort the render. |
| `Signal.get()`/tuple/`Option`/`Result` `.clone()` | Rust structural `Clone` | TS: duck-typed `typeof value?.clone === "function" ? value.clone() : value` (`browser/src/surrogate/signal.ts:22-25`, `option.ts:38-44`, `result.ts:71-78`) — falls back to returning the same reference (JS is reference-semantics for objects) when no `.clone` exists. | If a vocabulary type is added to Rust with real `Clone` semantics but its TS mirror lacks a `.clone()` method, the browser silently aliases instead of copying — a latent-bug shape, not proven to exist today but structurally possible given no static parity check (§1). |
| `Signal` write shorthand (`toggle`/`increment`/`decrement`/`push_str`) | Rust-side: `write_in_browser_only() -> !` — these methods **panic if ever called during server render** (`src/surrogate/signal.rs:107`, referenced via the `impl SignalSurrogate<bool>`/`<f64>`/`<String>` blocks at lines 54,66,88) | Browser-side: real `inner.set(prev => ...)` mutation via `@maverick-js/signals` (`browser/src/surrogate/signal.ts:31-45`) | Intentional asymmetry, not a bug: these are write-only, browser-only operations by design; a server-render code path exercising them is a compile-time-permitted but runtime-panicking configuration (only detected if the same expression is ever server-evaluated, e.g. accidentally used outside an event handler). |
| `.await` / async closures / `Procedure::call` | Rust `async`/`.await`, real `tokio` executor server-side | JS `await`, real network `fetch()` round-trip to `/_topcoat/procedures/{id}` for `Procedure.call` (`browser/dist/index.js` bundled `Procedure` class; source not separately inspected beyond bundle) — **not** a local computation, introduces real async network latency/failure modes (non-2xx throws) that have no equivalent risk on the server side (already-resolved value). | Different failure/timing model entirely; error message format for failed procedure calls (`Procedure call failed: {status} {statusText}`) is JS-specific text with no Rust-side counterpart to compare. |
| `NaN` comparisons | Rust `f64` `PartialOrd`/`PartialEq`: `NaN != NaN`, all ordering comparisons false | JS `NaN` semantics: `NaN !== NaN`, all relational comparisons false — **identical** IEEE-754 behavior on both sides via the direct `<`/`>`/`===` pass-through (`f64.ts:103-125`) | None. |
| `loop`/`while`/`break`/`continue` | Rust loop semantics | JS `while(true){}`/`while(cond){}` with native `break`/`continue` (`expr_loop.rs:14`, `expr_while.rs:16-18`) — cond dehydrated via `.dehydrate()` call inserted into JS (`expr_if.rs:39`, `expr_while.rs:18`) | None structurally; but an infinite `loop {}` compiled to JS `while(true){}` inside a synchronous `effect()` callback (`text.ts:19-27`) would hang the browser's single JS thread with no yielding — same risk profile as Rust but no `.await` opportunity for the JS event loop to intervene unless the loop body itself contains an `.await`. |

## 4. Standalone driving (external harness)

**No dedicated non-macro compile-single-expression API is exposed as a *public product surface*, but there is a usable path, demonstrated directly by the repo's own tests (`crates/topcoat-runtime/macro/tests/expr.rs`):**

1. **Rust → IL text.** `topcoat-runtime-grammar` (`crates/topcoat-runtime/grammar/Cargo.toml`) is a **plain library crate**, not a proc-macro crate — nothing prevents an external crate from depending on it directly and calling `topcoat_runtime_grammar::expr::Expr`'s `syn::parse2`/`expr_to_tokens()` (`grammar/src/expr.rs:39-45,54`) outside of proc-macro expansion. However `expr_to_tokens()` returns a Rust `TokenStream` with the JS string baked in as a literal argument to `__js(...)`/`__js_unescaped(...)` calls — there is no method that returns the raw JS `String` on its own; a harness would have to grep/parse the emitted `TokenStream` for the string literal(s), OR (simpler, and the pattern the test suite itself uses):
2. **Empirically extract IL by actually running the macro + rendering.** Depend on `topcoat` with `runtime`+`view` features (as `macro/Cargo.toml:26-28` dev-deps do), then in a tiny binary/test:
   ```rust
   use topcoat::{context::Cx, view::view};
   let cx = &Cx::default();
   let html = view! { cx => $(<your expression>) }.unwrap().render(cx);
   ```
   The rendered `html` string contains the JS text inside an HTML comment `<!-- ::topcoat::expr::start("<escaped js>") -->...<!-- ::topcoat::expr::end -->` (marker format/regex at `browser/src/comment.ts:20`). Extract with the same regex to recover the raw (HTML-entity-decoded) JS source. This is exactly the technique `macro/tests/expr.rs:11-23` etc. use to assert on generated JS content (`assert!(html.contains(".toggle()"))`).
3. **JS execution under plain Node, without DOM.** Do **not** `require`/import `browser/dist/index.js` directly as a library — its very last statement unconditionally runs `new Runtime().start(document)` at module-load time (bundle tail confirmed by direct read of `dist/index.js`; source: `browser/src/index.ts:1-3`, `import { Runtime } from "./runtime"; new Runtime().start(document);`), which calls `document.createTreeWalker` immediately and will throw `ReferenceError: document is not defined` in a bare Node process. Instead, bundle/import only the **DOM-free pure modules**: `browser/src/context.ts` (`Context` class, no DOM/window refs — only imports `./signal` and `./surrogate`), and `browser/src/surrogate/*.ts` (`f64.ts`, `string.ts`, `bool.ts`, `option.ts`, `result.ts`, `signal.ts`, `panic.ts`, `index.ts`'s `hydrateSurrogate`) — none of these touch `document`/`window`; `signal.ts` only depends on `@maverick-js/signals`, a pure-JS reactive-signals library with no DOM dependency. `browser/src/runtime.ts`, `scope.ts`, `scan.ts`, `text.ts`, `binding.ts`, `event.ts`, `comment.ts`(uses `DOMParser`) are the DOM-coupled modules to avoid. A minimal harness:
   ```ts
   import { Context } from ".../context";
   import { SignalRegistry } from ".../signal";
   const cx = new Context(new SignalRegistry());
   const fn = new Function("cx", `return ${js};`);
   const result = fn(cx);
   ```
   matching exactly the four production call sites' pattern (`binding.ts:27`, `event.ts:14`, `scope.ts:93`, `text.ts:15`). `Context` itself needs no DOM (`context.ts:16-46`); only `.hydrate()`/`.some()`/`.none()`/`.ok()`/`.err()`/`.signal()` are used from it by generated code.

## Notable structural findings for the generator/interpreter spec

- The grammar layer is **purely syntax-directed textual JS emission**, string-built in lockstep with real Rust token generation — there's no AST/IR object for the JS half at all, only a `String` accumulator (`js: &mut String` threaded through every `dispatch`/`expr_*` function). A from-scratch reference interpreter should treat "the IL" as **valid JavaScript expression syntax operating over method-chains on `cx`-reachable surrogate objects**, not a custom bytecode.
- The full instruction vocabulary methods generated onto surrogate objects are exactly: `add sub mul div neg eq ne lt le gt ge not deref` (from operators, `expr_binary.rs:20-29`, `expr_unary.rs:15-18`) plus whatever method name follows a `.` in source (unrestricted syntactically) plus `cx.hydrate(...)`, `cx.some(...)`, `cx.ok(...)`, `cx.err(...)`, `cx.none()` (literal/constructor emission, `expr_lit.rs:41`, `expr_call.rs:27,32,37`, `expr_path.rs:38`) plus `.call(...)` for closure invocation and `.dehydrate()` inserted automatically around `if`/`while` conditions (`expr_if.rs:39`, `expr_while.rs:18`).
- No integer types exist anywhere (i32/i64/u32/u64/usize all absent) — `f64` is the sole numeric type end-to-end, eliminating an entire class of wrapping/overflow-divergence risk by construction, confirmed by the literal-parsing whitelist rejecting everything but `Lit::Float`/`Lit::Bool`/`Lit::Str` (`expr_lit.rs:15-31`).
